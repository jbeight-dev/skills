# 버그 진단 스킬

---

## Phase 1 — 피드백 루프 만들기

> **이것이 이 스킬의 핵심이다.** 나머지는 모두 기계적인 절차에 가깝다.

버그에 대해 빠르고, 결정적이며, Agent가 실행할 수 있는 PASS/FAIL 신호가 있다면 원인을 찾을 수 있다. 이분 탐색, 가설 검증, 계측은 모두 그 신호를 활용하는 과정일 뿐이다. 그런 신호가 없다면 아무리 코드를 들여다봐도 문제를 해결하기 어렵다.

**여기에 과할 정도로 많은 노력을 들여라. 공격적으로 접근하고, 창의적으로 시도하고, 쉽게 포기하지 마라.**

### 피드백 루프를 만드는 방법

대략 이 순서로 시도한다.

| # | 방법 | 설명 |
|---|------|------|
| 1 | **실패하는 테스트** | 버그가 발생하는 지점까지 도달할 수 있는 단위 테스트, 통합 테스트, E2E 테스트를 사용한다. |
| 2 | **Curl / HTTP 스크립트** | 실행 중인 개발 서버를 대상으로 작성한다. |
| 3 | **CLI 명령** | fixture 입력값으로 실행하고, stdout을 정상 스냅샷과 비교한다. |
| 4 | **Headless Browser Script** | Playwright / Puppeteer로 UI를 조작하고 DOM, 콘솔, 네트워크를 검증한다. |
| 5 | **Trace 재생** | 실제 네트워크 요청, payload, 이벤트 로그를 디스크에 저장한 뒤 격리된 상태로 재실행한다. |
| 6 | **임시 Harness** | 시스템의 최소 부분만 띄우고, 의존성은 mock 처리하여 단일 함수 호출로 버그 경로를 실행한다. |
| 7 | **Property / Fuzz Loop** | 버그가 "가끔 잘못된 출력이 나오는 문제"라면 1000개의 랜덤 입력으로 실패 패턴을 찾는다. |
| 8 | **Bisection Harness** | 두 개의 알려진 상태(commit, dataset, version) 사이에서 발생했다면 `git bisect run`으로 자동화한다. |
| 9 | **Differential Loop** | 같은 입력을 구버전과 신버전, 또는 두 개의 설정에 넣고 결과 차이를 비교한다. |
| 10 | **HITL Bash Script** | 마지막 수단. 사람이 클릭해야 한다면 `scripts/hitl-loop.template.sh`로 사람의 작업도 구조화한다. |

> 올바른 피드백 루프를 만들면 **버그의 90%는 이미 해결된 것이다.**

### 루프 자체를 개선하라

루프를 하나의 제품처럼 다뤄라. 일단 루프를 만들었다면 다음을 질문한다.

- **더 빠르게** 만들 수 있는가? 설정을 캐시하거나, 관련 없는 초기화를 건너뛰거나, 테스트 범위를 좁힐 수 있는가?
- **신호를 더 명확하게** 만들 수 있는가? 단순히 "크래시가 나지 않았다"가 아니라, 구체적인 증상을 검증하고 있는가?
- **더 결정적으로** 만들 수 있는가? 시간을 고정하고, 난수 seed를 고정하고, 파일시스템을 격리하고, 네트워크를 고정할 수 있는가?

> 30초 걸리고 불안정한 루프는 루프가 없는 것과 크게 다르지 않다.
> 반면 **2초 만에 결정적으로 동작하는 루프는 디버깅의 강력한 무기**다.

### 비결정적 버그

목표는 완벽하게 깔끔한 재현이 아니라 **재현율을 높이는 것**이다.

트리거를 100번 반복하고, 병렬로 실행하고, 부하를 추가하고, 타이밍 구간을 좁히고, sleep을 주입하라.

- 50% 확률로 발생하는 flaky bug → 디버깅 가능
- 1% 확률 → 디버깅 어려움

디버깅 가능한 수준까지 재현율을 계속 높여라.

### 정말로 루프를 만들 수 없을 때

멈추고, 그 사실을 명확히 말하라. 무엇을 시도했는지 목록으로 정리하라. 사용자에게 다음 중 하나를 요청하라.

- 버그가 재현되는 환경에 대한 접근 권한
- HAR 파일, 로그 덤프, core dump, 타임스탬프가 포함된 화면 녹화 같은 캡처된 증거
- 운영 환경에 임시 계측을 추가할 수 있는 권한

> **루프 없이 가설 수립으로 넘어가지 마라.**
> 믿을 수 있는 루프가 생기기 전까지 Phase 2로 진행하지 마라.

---

## Phase 2 — 재현하기

루프를 실행하고, 실제로 버그가 발생하는 것을 확인하라.

다음을 검증한다.

- [ ] 루프가 사용자가 설명한 **바로 그 실패 현상**을 재현하는가? (비슷한 다른 오류가 아니어야 한다. 잘못된 버그를 잡으면 잘못된 수정으로 이어진다.)
- [ ] 실패가 여러 번 실행해도 재현되는가? (비결정적 버그라면, 디버깅 가능한 수준으로 충분히 높은 확률로 재현되는가?)
- [ ] 정확한 증상(에러 메시지, 잘못된 출력, 느린 응답 시간)을 캡처했는가? (이후 단계에서 수정이 실제 문제를 해결했는지 검증할 수 있어야 한다.)

> **버그를 재현하기 전까지 다음 단계로 넘어가지 마라.**

## Phase 3 — 가설 세우기

가설을 검증하기 전에 먼저 **우선순위가 있는 3~5개의 가설**을 만들어라.

하나의 가설만 생각하면 가장 먼저 떠오른 그럴듯한 아이디어에 사고가 고정된다.

### 반증 가능한 가설 형식

각 가설은 반드시 **반증 가능(falsifiable)** 해야 한다.

```
"만약 <X>가 원인이라면,
 <Y>를 변경했을 때 버그가 사라지거나,
 <Z>를 변경했을 때 문제가 더 심해질 것이다."
```

예측을 설명할 수 없다면, 그건 단지 느낌일 뿐이다. 버리거나 더 구체화하라.

### 사용자에게 먼저 공유하라

가설을 테스트하기 전에 우선순위 목록을 사용자에게 먼저 보여줘라. 사용자는 종종 즉시 우선순위를 바꿀 수 있는 도메인 지식을 가지고 있다.

> 예:
> - *"우리가 방금 #3 관련 배포를 했어요."*
> - *"그 가설은 이미 확인해봤어요."*

아주 작은 체크포인트지만 시간을 크게 절약해준다. 사용자가 자리에 없더라도 기다리지 말고, 현재 우선순위 기준으로 계속 진행하라.

## Phase 4 — 계측(Instrumentation)

각 probe(로그, 브레이크포인트, 측정)는 반드시 **Phase 3의 특정 가설과 연결**되어야 한다.
**한 번에 하나의 변수만 변경하라.**

### 도구 우선순위

1. **Debugger / REPL inspection** — 가능하다면 이것을 먼저 사용하라. 브레이크포인트 하나가 로그 열 개보다 낫다.
2. **정밀 로그** — 가설을 구분할 수 있는 경계 지점에만 정확히 필요한 로그를 추가하라.
3. **"전부 로그 찍고 grep" 방식은 절대 금지.**

### 디버그 로그 prefix 규칙

모든 디버그 로그에는 고유 prefix를 붙여라.

```
[DEBUG-a4f2] ...
```

이렇게 하면 마지막 cleanup 시 grep 한 번으로 제거할 수 있다.

| 종류 | 처리 |
|------|------|
| prefix **없는** 로그 | 살아남는다 |
| prefix **있는** 로그 | 제거 대상 |

### 성능 문제 분기

성능 회귀 문제에서는 로그가 대부분 도움이 안 된다. 대신 먼저 **baseline 측정**을 만들어라.

- timing harness
- `performance.now()`
- profiler
- query plan

그 후에 bisect 하라.

> **측정 먼저, 수정은 나중.**

## Phase 5 — 수정 + 회귀 테스트

수정을 하기 전에 먼저 **regression test(회귀 테스트)를 작성하라.**
단, 테스트를 넣기에 적절한 올바른 seam(접점)이 존재할 때만 그렇게 한다.

### 올바른 seam이란?

실제 호출 환경에서 발생한 진짜 버그 패턴을 테스트가 재현할 수 있는 위치를 의미한다.

> 예를 들어, 실제 버그는 여러 caller가 동시에 호출해야 발생하는데,
> 단일 caller만 검증하는 shallow unit test를 작성하면
> 그 테스트는 **거짓된 안정감**을 줄 뿐이다.

### seam이 없을 때

만약 적절한 seam이 없다면, 그 자체가 중요한 발견이다.

> **현재 아키텍처가 버그를 테스트로 고정할 수 없게 만들고 있다**는 의미다.

이 사실을 기록하고 다음 단계로 넘겨라.

### seam이 존재할 때 — 수정 절차

1. 최소화된 repro를 실패하는 테스트로 만든다.
2. 실제로 실패하는지 확인한다.
3. 수정 적용
4. 테스트가 통과하는지 확인
5. 원래의 전체 시나리오(최소화되지 않은 실제 흐름)에 대해 Phase 1 루프를 다시 실행한다.

## Phase 6 — 정리 + 사후 분석

### 완료 선언 전 체크리스트

- [ ] 원래 repro가 더 이상 재현되지 않는다 (Phase 1 루프 재실행)
- [ ] Regression test 통과 (또는 seam 부재가 문서화됨)
- [ ] 모든 `[DEBUG-...]` 계측 제거 (grep으로 확인)
- [ ] 임시 prototype 삭제 (또는 명확한 debug 위치로 이동)
- [ ] 최종적으로 맞았던 가설을 commit / PR 메시지에 기록 → 다음 디버거가 학습할 수 있도록

### 사후 분석 질문

완료 후 다음을 질문하라.

> "이 버그를 애초에 예방할 수 있었던 방법은 무엇인가?"

만약 답이 아키텍처 문제라면 — 예를 들어:

- 테스트 seam 부재
- 꼬인 caller 구조
- 숨겨진 coupling

— `/improve-codebase-architecture` 스킬로 넘겨라.

> **아키텍처 개선 제안은 버그 수정 후에 하라.**
> 지금은 처음보다 훨씬 더 많은 정보를 가지고 있기 때문이다.
