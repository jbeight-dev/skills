---
name: grill-with-docs
description: 기존 도메인 모델과 문서를 기준으로 계획을 검증하고, 용어를 정교화하며, 의사결정이 구체화될 때 CONTEXT.md 및 ADR 문서를 함께 갱신하는 grilling 세션. 사용자의 계획을 프로젝트의 언어 및 문서화된 결정 기준으로 스트레스 테스트하고 싶을 때 사용한다.
---

해야 할 일

사용자와 완전히 같은 이해에 도달할 때까지 이 계획의 모든 측면에 대해 집요하게 질문하라. 설계 트리의 각 분기를 따라 내려가며, 의사결정 간 의존성을 하나씩 해결하라. 각 질문마다 권장 답변도 함께 제시하라.

질문은 한 번에 하나씩만 하며, 사용자의 피드백을 받은 뒤 다음 질문으로 진행하라.

질문에 대한 답이 코드베이스 탐색으로 가능하다면, 사용자에게 묻지 말고 코드베이스를 직접 탐색하라.

⸻

보조 정보

도메인 인식(Domain awareness)

코드베이스를 탐색할 때 기존 문서도 함께 확인하라.

파일 구조

대부분의 저장소는 하나의 context를 가진다.

/ 
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/

만약 루트에 CONTEXT-MAP.md 가 존재한다면, 저장소는 여러 context를 가진다.
이 map은 각 context가 어디에 있는지 가리킨다.

/ 
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전체 의사결정
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context 전용 의사결정
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/

파일은 필요할 때만 생성하라.

* CONTEXT.md 가 없다면, 첫 번째 용어가 정리될 때 생성한다.
* docs/adr/ 가 없다면, 첫 번째 ADR이 필요할 때 생성한다.

⸻

세션 중 해야 할 일

Glossary와 충돌하는지 검증

사용자가 기존 CONTEXT.md 의 언어와 충돌하는 용어를 사용하면 즉시 지적하라.

예:

당신의 glossary에서는 'cancellation'을 X로 정의했는데,
지금은 Y 의미로 사용하는 것 같습니다.
어느 쪽이 맞습니까?

⸻

모호한 언어를 정교화

사용자가 모호하거나 여러 의미로 사용될 수 있는 용어를 쓰면,
정확한 canonical term(표준 용어)을 제안하라.

예:

지금 'account' 라고 표현했는데,
Customer를 의미합니까? User를 의미합니까?
둘은 다른 개념입니다.

⸻

구체적인 시나리오 논의

도메인 관계를 논의할 때는 실제 시나리오로 검증하라.

경계 조건(edge case)을 드러내고,
개념 간 경계를 명확하게 만들 수 있는 시나리오를 만들어 질문하라.

⸻

코드와 교차 검증

사용자가 “현재 시스템은 이렇게 동작한다”고 말하면,
코드가 실제로도 그렇게 동작하는지 확인하라.

모순이 있다면 드러내라.

예:

코드에서는 전체 Order만 취소하는데,
방금 partial cancellation이 가능하다고 설명했습니다.
어느 쪽이 실제 동작입니까?

⸻

CONTEXT.md를 즉시 갱신

용어가 합의되면 즉시 CONTEXT.md 를 업데이트하라.

한꺼번에 몰아서 정리하지 말고,
결정되는 즉시 기록하라.

형식은 CONTEXT-FORMAT.md 를 따른다.

중요:

CONTEXT.md 는 구현 상세를 포함하면 안 된다.

다음처럼 사용해서는 안 된다.

* 구현 명세(spec)
* 임시 메모장(scratch pad)
* 구현 의사결정 저장소

CONTEXT.md 는 오직 glossary(용어집) 역할만 해야 한다.

⸻

ADR은 신중하게 제안

다음 세 가지가 모두 참일 때만 ADR 생성을 제안하라.

1. 되돌리기 어렵다
    → 나중에 변경 비용이 크다
2. 배경 설명 없이는 이해하기 어렵다
    → 미래의 독자가 “왜 이렇게 만들었지?” 라고 궁금해할 수 있다
3. 실제 trade-off 결과다
    → 여러 대안이 있었고, 특정 이유로 하나를 선택했다

셋 중 하나라도 없으면 ADR을 만들지 마라.

형식은 ADR-FORMAT.md 를 따른다.
